# Database schema (implemented)

PostgreSQL is the source of truth. Drizzle definitions are in server/src/db/schema.ts; generated SQL and snapshots are in server/drizzle.

The current runtime uses local PostgreSQL managed in pgAdmin 4, with the existing `DATABASE_URL` and `DB_SSL=false`. No cloud synchronization or Neon configuration is part of Phase 4.

| Table             | Fields and relationships                                                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| departments       | UUID, name, description, active, created/updated timestamps                                                                                                    |
| users             | UUID, full_name, case-insensitive unique email, nullable password_hash pending provisioning, role, account_status, department_id, last_login_at, timestamps    |
| ticket_categories | UUID, name, description, active, timestamps                                                                                                                    |
| tickets           | UUID, identity ticket_number, subject, description, category_id, priority, status, requester_id, assigned_agent_id, created/updated/resolved/closed timestamps |
| ticket_comments   | UUID, ticket_id, author_id, message, is_internal, timestamps                                                                                                   |
| ticket_activity   | UUID, ticket_id, actor_id, action, old_value, new_value, is_internal, created_at                                                                               |
| sessions          | UUID, user_id, unique token_hash, expires_at, created_at, revoked_at                                                                                           |

Departments have many users. Users request tickets and may be assigned tickets as eligible active agents. Categories have many tickets. Tickets have many comments and activity entries. Users author comments/activity and own sessions.

All timestamps use PostgreSQL timestamptz and APIs serialize ISO UTC dates. UUIDs are generated by PostgreSQL. Ticket numbers use a database identity sequence; rollbacks can leave gaps, but concurrent requests cannot generate duplicates. The UI displays RD- followed by that number.

## Constraints and indexes

- Unique lower(email) index; input emails normalize to lowercase. Optional usernames have their own unique lower(username) index and a database format constraint (3-32 lowercase letters, numbers, dots, hyphens, or underscores; the first character must be a letter, number, or underscore).
- Case-insensitive unique department/category names.
- Foreign keys explicitly RESTRICT deletion; support history is never cascade-deleted.
- Status, priority, role, and account status are PostgreSQL enums.
- Check constraint: resolved/closed statuses require resolved_at; only closed has closed_at.
- Indexes for requester/assignee + updated_at, status/priority, category, created_at, comment/activity chronology, session token/expiry/user, and user department/role/status.
- Assignment eligibility is enforced transactionally by the service; direct database writers must preserve that invariant.

## Phase 3 attachments and conversations

Migration `0005_bright_wraith.sql` adds:

- `ticket_attachments`: ticket/comment/uploader/submission foreign keys, UUID storage key, safe display filename, MIME, byte size, visibility, timestamps and deletion tombstone. Files remain on private disk. Checks restrict MIME and size; a composite foreign key prevents linking a comment from another ticket.
- `ticket_submissions`: caller-supplied UUID, authenticated actor, operation kind, content fingerprint, committed ticket ID and replay result. The primary key serializes duplicate submissions.
- `conversation_reads`: composite ticket/user primary key, nonnegative monotonic position and update timestamp.
- `response_templates`: title, body, author, active flag and timestamps; length constraints and active/title index.
- `ticket_comments.position`: generated identity with unique and ticket/position indexes; existing comments receive positions while all original fields remain intact. The ticket/comment unique index must exist before the attachment composite foreign key.

All new foreign keys restrict deletion. No role or status enum changes, account replacement, credential changes or data resets are involved. Services enforce public/internal visibility and same-ticket attachment consistency. SQL access is parameterized and uses the existing pool. See [storage transaction boundaries](attachments-conversations.md).

## Migrations

Phase 4 migration `0006_equal_sunspot.sql` creates five tables without changing existing rows or columns: `operation_events` (unique business-event key, pending index), `notifications` (unique event/recipient pair, recipient date/unread indexes), `notification_preferences` (one row per user), `sla_policies` (one per existing priority, bounded targets/calendar), and `ticket_slas` (unique ticket/cycle, policy snapshot, deadlines, outcome timestamps, indexed next check). Foreign keys restrict deletion. The migration inserts four initial demonstration policies only; it does not reseed accounts or tickets. See [Phase 4 data and processing rules](phase4-operations.md).

Phase 3.2 adds `tickets.assignment_version` (nonnegative, default zero) in `0003_gray_mysterio.sql`. Migration `0004_tricky_zzzax.sql` adds `ticket_escalations` with ticket/requesting-user foreign keys, reason, separate status, acknowledging/resolving users and timestamps. All foreign keys restrict deletion. A partial unique index prevents more than one open/acknowledged escalation per ticket. Check constraints validate state metadata and reason length; indexes support ticket history and state/date queues. Existing account, ticket, session and activity rows remain untouched. See [assignment/escalation details](assignment-escalation.md).

Phase 3.1 migration `0002_sticky_garia.sql` is additive:

- `tickets.resolved_by` and `tickets.closed_by`: nullable user foreign keys with restricted deletion.
- `tickets.resolution_summary`: nullable public summary for the current resolution attempt.
- `tickets.lifecycle_version`: nonnegative integer, default 0.
- `ticket_activity.explanation`: nullable public resolution summary or closure/reopening reason for lifecycle events.
- `ticket_activity.lifecycle_version`: nullable integer with a unique `(ticket_id, lifecycle_version)` index. Historical rows retain null versions.
- Consistency checks require summary/actor pairs and valid lifecycle state for new resolution metadata. Existing resolved/closed rows without structured notes remain valid.

No table, status, user, credential, session, ticket, or prior history is removed or recreated. Reopening clears only the current ticket's resolution/closure fields; prior summaries remain in activity events. Original creation dates and assignments remain unchanged.

From the root, run npm run db:generate -w server after schema edits, review SQL, and run npm run db:migrate -w server. Generation requires no credentials. Application requires the server environment. The migration ledger prevents duplicate applications. No automatic reset, deletion, or seed occurs at startup.

Development seeds are explicit, guarded, and preserve existing passwords. Accounts without password_hash cannot authenticate or be activated through the API. Accounts and reference records are suspended/archived instead of hard-deleted.

## Validation boundary

Generated SQL is applied in isolated PostgreSQL tests. Default tests use PGlite for fast regression and disk reopen checks. `npm run test:postgres` creates a separate local `resolvedesk_test_*` database per suite for native PostgreSQL tests, including real pooled-connection contention, rollback, permissions, and lifecycle persistence. `npm run test:e2e:postgres` uses another separate local test database for browser workflows. Both retain their databases for inspection and print their names without credentials. Hosted networking/TLS and deployment behavior remain future checks.
