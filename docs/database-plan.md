# Database schema (implemented)

PostgreSQL is the source of truth. Drizzle definitions are in server/src/db/schema.ts; generated SQL and snapshots are in server/drizzle.

| Table             | Fields and relationships                                                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| departments       | UUID, name, description, active, created/updated timestamps                                                                                                    |
| users             | UUID, full_name, case-insensitive unique email, nullable password_hash pending provisioning, role, account_status, department_id, last_login_at, timestamps    |
| ticket_categories | UUID, name, description, active, timestamps                                                                                                                    |
| tickets           | UUID, identity ticket_number, subject, description, category_id, priority, status, requester_id, assigned_agent_id, created/updated/resolved/closed timestamps |
| ticket_comments   | UUID, ticket_id, author_id, message, is_internal, timestamps                                                                                                   |
| ticket_activity   | UUID, ticket_id, actor_id, action, old_value, new_value, is_internal, created_at                                                                               |
| sessions          | UUID, user_id, unique token_hash, expires_at, created_at, revoked_at                                                                                           |

Departments have many users. Users request tickets and may be assigned tickets as eligible active agents. Categories have many tickets. Tickets have many comments and activity entries. Users author comments/activity and own sessions.

All timestamps use PostgreSQL timestamptz and APIs serialize ISO UTC dates. UUIDs are generated by PostgreSQL. Ticket numbers use a database identity sequence; rollbacks can leave gaps, but concurrent requests cannot generate duplicates. The UI displays RD- followed by that number.

## Constraints and indexes

- Unique lower(email) index; input emails normalize to lowercase.
- Case-insensitive unique department/category names.
- Foreign keys explicitly RESTRICT deletion; support history is never cascade-deleted.
- Status, priority, role, and account status are PostgreSQL enums.
- Check constraint: resolved/closed statuses require resolved_at; only closed has closed_at.
- Indexes for requester/assignee + updated_at, status/priority, category, created_at, comment/activity chronology, session token/expiry/user, and user department/role/status.
- Assignment eligibility is enforced transactionally by the service; direct database writers must preserve that invariant.

## Migrations

From the root, run npm run db:generate -w server after schema edits, review SQL, and run npm run db:migrate -w server. Generation requires no credentials. Application requires the server environment. The migration ledger prevents duplicate applications. No automatic reset, deletion, or seed occurs at startup.

Development seeds are explicit, guarded, and preserve existing passwords. Accounts without password_hash cannot authenticate or be activated through the API. Accounts and reference records are suspended/archived instead of hard-deleted.

## Validation boundary

Generated SQL is applied in isolated PostgreSQL tests, including unique/foreign-key checks, transactional rollback, repeat migration, and disk reopen persistence. Neon connectivity/TLS and concurrent multi-connection locking require a dedicated Neon validation pass.
