# Private attachments and support collaboration

Phase 3.3–3.5 extends the existing ticket and comment workflows. The local PostgreSQL database, authentication, roles, lifecycle, assignment and escalation services remain in use. No cloud storage or Neon is configured. Phase 4 now adds [authenticated live updates and persistent notifications](phase4-operations.md) to these workflows.

## Storage and maintenance

Attachment metadata lives in `ticket_attachments`. File bytes live in a private directory through `PrivateStorage.put/get/remove`. The default is `<repository>/uploads`, ignored by Git and never exposed as a static route. UUID v4 storage keys are generated by the server; original filenames are display metadata only. API responses do not expose storage keys or absolute paths.

| Setting                    | Default    | Constraints                                              |
| -------------------------- | ---------- | -------------------------------------------------------- |
| `UPLOAD_DIR`               | `uploads`  | Dedicated private directory; relative to repository root |
| `UPLOAD_MAX_FILE_BYTES`    | `10485760` | Positive, at most 10 MiB                                 |
| `UPLOAD_MAX_FILES`         | `5`        | 1–5 files per submission                                 |
| `UPLOAD_MAX_REQUEST_BYTES` | `53477376` | Aggregate request cap, including multipart overhead      |

Existing environments can use defaults without modification. Custom directories must also be excluded from Git and web serving. On Windows, restrict the directory's ACL to the application account; POSIX mode arguments alone do not configure Windows ACLs. Back up the database and private files together. Moving storage requires copying existing UUID objects and changing configuration together.

The parser accepts PNG, JPEG, WEBP, PDF and conservative UTF-8 TXT. It detects binary file signatures and checks extension and declared MIME agreement. TXT rejects invalid UTF-8, control bytes, markup and shebang content. Filename validation rejects traversal, path separators, alternate data streams and control/bidirectional characters. Files are not malware-scanned or fully decoded by image/PDF codecs. Downloads are attachments with `nosniff`, a sandbox CSP and private no-store responses; they are not rendered inline. Only locally selected image files receive browser previews.

Requests have bounded file/field/part counts, per-file and aggregate byte limits, and a 60-second parsing deadline. At most two multipart submissions are processed concurrently per API process. Files are buffered within these bounds before writes. A future multi-replica deployment needs shared storage and coordinated resource controls.

### Consistency and recovery

Ticket or comment creation, file metadata, audit entries and submission result commit in one PostgreSQL transaction. Private file writes occur before commit; ordinary disk/database failures and detected cancellation roll back database changes and remove attempted objects. A process crash between a file write and commit can leave an inaccessible orphan. A cancellation after commit can leave a successful submission whose response was lost; retry the unchanged submission identifier to recover its result.

Deletion commits a tombstone and audit record before removing the physical object. Failed disk deletion cannot restore download access. Missing objects return a safe 404. Records, comments and ticket history are retained.

Inspect consistency with the development-only, read-only default:

```powershell
npm run storage:audit -w server
```

The report lists counts of missing active objects, orphans and deleted objects. Review the report and backups before explicitly cleaning orphaned/deleted UUID objects older than 24 hours:

```powershell
npm run storage:audit -w server -- --cleanup
```

Cleanup never deletes database rows or active referenced files. It is not a scheduled retention policy and cannot recover missing files. No cleanup runs at application startup.

## API contracts

All paths below use `/api`. Authentication is required. Mutations retain exact-origin and CSRF checks. Uploads use `multipart/form-data`; let the browser supply its boundary. Ordinary JSON calls remain supported for ticket creation and comments without files.

| Method / path                         | Input or result                                                                            |
| ------------------------------------- | ------------------------------------------------------------------------------------------ |
| `GET /attachment-limits`              | Configured file/count/request limits                                                       |
| `POST /tickets`                       | Existing ticket fields, optional files and submission ID; atomic ticket plus files         |
| `POST /tickets/:id/comments`          | `message`, `isInternal`, optional files and submission ID; atomic comment plus files       |
| `POST /tickets/:id/attachments`       | Files, `submissionId`, optional `isInternal` (false default), optional `commentId`         |
| `GET /tickets/:id/attachments`        | Visible, nondeleted safe metadata with uploader, date, size, MIME and `canDelete`          |
| `GET /attachments/:id/download`       | Authenticated attachment response; inaccessible/missing objects return 404                 |
| `DELETE /attachments/:id`             | Empty JSON body; uploader or administrator, within current ticket scope                    |
| `GET /tickets/:id/comments`           | Existing chronological comments, with author role, position and viewer-specific `isUnread` |
| `GET /tickets/:id/conversation-state` | `unreadCount`, `latestPosition`, `lastPosition`                                            |
| `POST /tickets/:id/read`              | `{ "throughPosition": 12 }`; visible message in this ticket or zero                        |
| `GET /response-templates`             | Support-only shared active templates; page, limit (up to 100), title search                |
| `POST /response-templates`            | `title` (2–100), `body` (1–5000); author comes from session                                |
| `PATCH /response-templates/:id`       | Same title/body fields; creator or administrator                                           |
| `DELETE /response-templates/:id`      | Empty JSON body; creator/admin archives the template                                       |

Each file is submitted under `files`. Multipart booleans are exactly `true` or `false`. Unknown fields, repeated fields, unsafe filenames, invalid content and empty files fail validation. Unsupported bodies use 415, oversized uploads 413, busy upload slots 429, and malformed input 400. Messages require nonblank text even when they include attachments.

The UI supplies a UUID `submissionId` for every ticket/reply/upload. Keep it unchanged when retrying the same body and files; change it when editing the submission. Matching retries return the committed result without duplicates. Reusing it for different content returns 409. Legacy JSON requests without files may omit it, but then have no caller-controlled retry deduplication. Submission records currently have no automatic expiry.

Employees can access only their own public ticket content. Agents can access only currently assigned tickets; administrators can access all tickets. Both file and parent-comment visibility are checked. Uploads to an existing comment must match its visibility and require the author or administrator. Employees cannot create internal content. Deletion requires current ticket access and uploader/admin permission. All access decisions are made on the server.

## Conversation behavior

The existing `ticket_comments` table and endpoints remain the conversation source. The UI shows author, role, time, public/internal label, text and files in chronological order. Internal notes and their files are excluded from employee queries. React escapes message text; no HTML editor or raw HTML rendering was introduced.

`conversation_reads` stores one cursor per ticket/user. PostgreSQL-generated comment positions provide stable progress markers. Cursor updates use `greatest` so an older browser response cannot move the cursor backward. Only another author's visible comments contribute to unread counts; internal notes never affect employee counts. Counts are batched for ticket-list pages. Opening the conversation marks loaded positions read and persists across refreshes/app restarts.

Support users manage saved replies in **Settings**. All active support templates can be searched and inserted; agents edit/archive their own templates, while administrators manage all. Selecting one inserts editable text and never sends it automatically. Templates persist in PostgreSQL and pass normal message validation when posted.

Conversations refresh after sending, on window focus and through **Refresh**. No live-delivery indicator is fabricated. A chronological thread was retained to preserve the existing comment model and straightforward visibility rules; nested reply-to threads are not implemented. Full history is returned currently; pagination for very long conversations is future work.

## Frontend integration

- **Create ticket:** keyboard-accessible picker, drag/drop, safe local image previews, file removal, count/size errors, actual upload progress and cancellation.
- **Ticket detail:** standalone public attachments, guarded download, authorized delete confirmation, feedback and refreshed metadata.
- **Conversation:** public/internal composer, shared picker, template insertion, role identities and unread markers. Failed submissions retain text/files for retry.
- **Ticket lists:** real unread counts and UUID-based links while preserving the `RD-` display number.
- **Settings:** template search, pagination, creation, editing and archive confirmation for support roles.

## Local migration

With the existing PostgreSQL service running and existing `server/.env` preserved:

```powershell
npm run db:migrate -w server
npm run dev
```

Migration `0005_bright_wraith.sql` adds four tables, comment positions, constraints and indexes. Its composite attachment/comment foreign key follows creation of the required unique index. The ledger makes repeated migration commands safe. Do not reset, push the schema or reseed an existing installation. No credential, role or existing account update is required.

## Three-role manual walkthrough

Use the existing local demo logins from the README; log out when switching roles.

1. **Mon (`monmon` / `monmon`):** create a printer ticket with a PNG or PDF. Open it from My Tickets. Download the file and post a public reply. Try a disallowed extension to see validation.
2. **Jayr (`jear` / `jear`):** assign the ticket to George. Check the workload display and assignment history. Inspect its attachment list and activity.
3. **George (`geor` / `geor`, Agent in Human Resources):** open the assigned ticket, create a saved reply under Settings, insert and edit it, then post a public reply with a TXT file. Add an internal note with a different file. Confirm internal content is labeled. Request escalation if appropriate.
4. **Jayr:** acknowledge and resolve the escalation. Confirm assignment and lifecycle history are intact. Edit/archive a saved reply if desired.
5. **Mon:** refresh the ticket, download the public file and confirm the internal note/file are absent. Public replies appear unread until viewed. Reload to confirm the read cursor persists. Deleting an own upload asks for confirmation; cancel first, then confirm on a disposable file.
6. **George:** move the ticket into progress and resolve with a summary. **Mon:** reopen with a reason. **George:** resolve again. **Mon:** confirm resolution and inspect the preserved history.

These steps intentionally add demo records. Automated write tests instead use isolated PostgreSQL databases and temporary private storage. See the [verification record](verification.md) for executed checks and preservation results.

## Integration and limits

Persisted ticket events, comments, read cursors and the storage adapter integrate with the Phase 4 outbox, notifications and SLA services. No malware scanner, full file-content disarm, nested conversation threads, automatic template seeding, conversation pagination, background orphan cleanup or distributed upload limiting is included. Local files need coordinated backups; production object storage, deployment and operational hardening remain separate work.
